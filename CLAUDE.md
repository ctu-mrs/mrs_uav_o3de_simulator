# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Multirotor drone simulation in O3DE (engine `o3de-sdk` 26.05 at `/opt/O3DE/26.05`) with a ROS 2 Jazzy interface. The repo root is the O3DE project `DroneSim`, created from the `Ros2ProjectTemplate`.

Design decision: dynamics run entirely inside O3DE (PhysX rigid body). The fast loop (attitude/rate control, mixer, motor model) runs inside O3DE at the physics rate; ROS 2 only carries attitude or attitude-rate + collective-throttle commands in and sensor data out. There is no lockstep with an external simulator.

## Build and test

ROS 2 must also be sourced before starting the Editor or Asset Processor. Otherwise the asset builders cannot load the ROS and Multirotor Gems and silently compile prefabs without those components while reporting success; the drone then has no topics. To recover, delete the affected `.spawnable` files under `Cache/linux` and run `AssetProcessorBatch` with ROS sourced.

ROS 2 must be sourced for every configure and build (the `ROS2Controllers` Gem requires `control_msgs` and `ackermann_msgs`):

```sh
source /opt/ros/jazzy/setup.zsh
CC=clang CXX=clang++ cmake -B build/linux -S . -G "Ninja Multi-Config"
cmake --build build/linux --config profile --target Editor DroneSim.GameLauncher -j 8   # full project
cmake --build build/linux --config profile --target Multirotor Multirotor.Editor -j 8    # Gem only, fast iteration
```

Unit tests (Multirotor controller):

```sh
cmake --build build/linux --config profile --target Multirotor.Tests -j 8
cd build/linux/bin/profile && ./AzTestRunner ./libMultirotor.Tests.so AzRunUnitTests
# single test: append --gtest_filter='MultirotorControllerTest.MixRollTorque*'
```

Keep `-j` at 8 or lower; the machine has 14 GB RAM.

## Architecture

- `Gem/` — project Gem generated by the template (sample component only).
- `Gems/Multirotor/` — the simulation code:
  - `MultirotorController` — pure AzCore math, no PhysX/ROS: attitude P → inertia-normalized rate PID (+ gyroscopic feed-forward) → minimum-norm allocation `A^T (A A^T)^-1` → first-order motor lag. Unit-tested.
  - `MultirotorConfiguration` — reflected rotor layout (empty selects `DefaultRotors()`: quad X, PX4 motor order), motor coefficients, gains, topics. Don't preset reflected vectors in a constructor: deserialization appends to them.
  - `MultirotorComponent` — requires `ROS2Frame` and a dynamic rigid body. Subscribes to `cmd/attitude` (`geometry_msgs/PoseStamped`: `pose.orientation` + throttle in `pose.position.z`) and `cmd/attitude_rate` (`geometry_msgs/TwistStamped`: body rate in `twist.angular` + throttle in `twist.linear.z`), namespaced by the entity's ROS2Frame. The interface uses standard messages only. On every PhysX sub-step (`OnSceneSimulationStart`) it steps the controller and applies per-rotor thrust as impulses at the rotor hubs plus the yaw reaction torque. Throttle is cut after `CommandTimeout` of sim time without commands. The body stays kinematic until a downward ray finds ground, or for `GroundWaitTimeout`, because a splat's collision mesh takes seconds to cook after physics starts. It also spins each rotor's `Visual` entity from the simulated rotor speed, slowed by `VisualSlowdown` to avoid aliasing.
- Sensors (IMU, odometry, cameras, lidar) come from the `ROS2Sensors` Gem components placed on the drone prefab, not from this code. IMU and odometry run at 250 Hz, as the MRS UAV System expects; odometry is relative to the spawn point, with twist in the body frame. A forward-facing RGB camera (`camera` entity, 640x480) publishes `/uav1/camera_image_color`; it needs a real renderer, not `--rhi=null`, and `AllowPipelineModification` in `Registry/ros2.setreg` so that Gems such as ModelForgeSplat can draw into its pipeline. The game view uses the `follow_camera` entity behind the drone; C switches to `free_camera` (`FreeCameraComponent`), with WASD, Q/E, and the right mouse button to look around.
- Everything crossing the ROS boundary is batched per rendered frame, including `/clock` and incoming commands, while physics keeps real time. Run with `--t_simulationTickDeltaOverride=17000` (microseconds): every frame then advances sim time by 17 ms, and slow frames slow the simulation instead of looking like dropouts to ROS. On the integrated GPU here, that gives 20 to 30 FPS and a realtime factor of 0.35 to 0.5 with the MRS UAV System running; `--r_renderScale=0.35` reaches about 45 FPS and 0.75 by lowering the game view resolution, without affecting the ROS camera. Don't use the ROS2 Gem's `realtime` clock: sensors pace themselves on it and lose samples.
- The MRS UAV System connects through the `mrs_uav_o3de_api` HW API plugin in `~/ws_o3de/src`. Spawn height and motor coefficients there must match this repo.
- `Tools/convert_x500_meshes.py` — bakes the x500 meshes and SDF poses from `~/git/mrs_uav_gazebo_simulation` into OBJ models in `Assets/Drone/x500/` (O3DE imports neither `.dae` nor colored `.stl`).
- `Tools/create_drone_prefab.py` — standalone generator for `Assets/Drone/Multirotor.prefab` and its instance in `DemoLevel` (entity `uav1`, topics under `/uav1`). It writes JSON because the Editor Python API cannot create a prefab from level entities, and takes the x500 rotor layout, colliders, and inertia from the SDF. Run the Asset Processor between the two tools: the prefab references the models by asset id.

Conventions: body frame is FLU (O3DE and ROS agree, Z up). Throttle ∈ [0,1] is proportional to rotor speed, so total thrust = N·k_f·(throttle·ω_max)²; this matches the MRS throttle model with a zero offset.

## Configuration notes

- PhysX fixed timestep is 2 ms (`Registry/physxsystemconfiguration.setreg`); the controller runs at that rate.
- Spawnables store serialized component data and are not rebuilt when a Gem library changes. After changing a component's serialized fields or defaults, delete the affected `.spawnable` files under `Cache/linux` and run `AssetProcessorBatch`, or the game keeps using the old values.
- The game reads a compiled copy of `Registry/*.setreg` from `Cache/linux/bootstrap.*.setreg`, so run the Asset Processor after changing them.
- External Gems (`ROS2` 4.3.0, `LevelGeoreferencing`, `ROS2Sensors`, `ROS2Controllers`, ...) live in `~/O3DE/Gems` and are registered in `~/.o3de/o3de_manifest.json`, not vendored in this repo.
- `.gitattributes` with Git LFS was intentionally dropped (git-lfs is not installed).
