# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Multirotor drone simulation in O3DE (engine `o3de-sdk` 26.05 at `/opt/O3DE/26.05`) with a ROS 2 Jazzy interface. The repo root is the O3DE project `DroneSim`, created from the `Ros2ProjectTemplate`.

Design decision: dynamics run entirely inside O3DE (PhysX rigid body). The fast loop (attitude/rate control, mixer, motor model) runs inside O3DE at the physics rate; ROS 2 only carries attitude or attitude-rate + collective-throttle commands in and sensor data out. There is no lockstep with an external simulator.

## Build and test

ROS 2 must be sourced for every configure and build (`mrs_msgs`, `control_msgs`, `ackermann_msgs` are required):

```sh
source /opt/ros/jazzy/setup.zsh
CC=clang CXX=clang++ cmake -B build/linux -S . -G "Ninja Multi-Config"
cmake --build build/linux --config profile --target Editor DroneSim.GameLauncher -j 8   # full project
cmake --build build/linux --config profile --target Multirotor Multirotor.Editor -j 8    # Gem only, fast iteration
```

Unit tests (Multirotor controller):

```sh
cmake --build build/linux --config profile --target Multirotor.Tests -j 8
cd build/linux/bin/profile && ./AzTestRunner ./libMultirotor.Tests.so AzRunUnitTests
# single test: append --gtest_filter='MultirotorControllerTest.MixRollTorque*'
```

Keep `-j` at 8 or lower; the machine has 14 GB RAM.

## Architecture

- `Gem/` — project Gem generated by the template (sample component only).
- `Gems/Multirotor/` — the simulation code:
  - `MultirotorController` — pure AzCore math, no PhysX/ROS: attitude P → inertia-normalized rate PID (+ gyroscopic feed-forward) → minimum-norm allocation `A^T (A A^T)^-1` → first-order motor lag. Unit-tested.
  - `MultirotorConfiguration` — reflected rotor layout (default: quad X, PX4 motor order), motor coefficients, gains, topics.
  - `MultirotorComponent` — requires `ROS2Frame` and a dynamic rigid body. Subscribes to `mrs_msgs/HwApiAttitudeCmd` and `HwApiAttitudeRateCmd` (namespaced by the entity's ROS2Frame). On every PhysX sub-step (`OnSceneSimulationStart`) it steps the controller and applies per-rotor thrust as impulses at the rotor hubs plus the yaw reaction torque. Throttle is cut after `CommandTimeout` of sim time without commands.
- Sensors (IMU, odometry, cameras, lidar) come from the `ROS2Sensors` Gem components placed on the drone prefab, not from this code.

Conventions: body frame is FLU (O3DE and ROS agree, Z up). Throttle ∈ [0,1] is proportional to rotor speed, so total thrust = N·k_f·(throttle·ω_max)²; this matches the MRS throttle model with a zero offset.

## Configuration notes

- PhysX fixed timestep is 2 ms (`Registry/physxsystemconfiguration.setreg`); the controller runs at that rate.
- External Gems (`ROS2` 4.3.0, `LevelGeoreferencing`, `ROS2Sensors`, `ROS2Controllers`, ...) live in `~/O3DE/Gems` and are registered in `~/.o3de/o3de_manifest.json`, not vendored in this repo.
- `.gitattributes` with Git LFS was intentionally dropped (git-lfs is not installed).
